# 26 构建、测试、CI 与发布

一个 13 包、1900+ 文件的 monorepo，靠一套相当严格的工程纪律维持。这一章讲「怎么改这个仓库」。

## 1. 构建顺序不是随便排的

根 `package.json`：

```json
"build": "cd packages/chord && npm run build && cd ../tui && npm run build &&
          cd ../telemetry && ... && cd ../ai && ... && cd ../durable && ...
          cd ../env && ... cd ../agent && ... cd ../protocol && ...
          cd ../client && ... cd ../server && ... cd ../coding-agent && npm run build"
```

顺序 = **拓扑序**：被依赖的先构建。

```
chord, tui, telemetry, codemode, mcp     ← 零内部依赖
  ↓
ai
  ↓
durable, env, agent
  ↓
protocol, client, server
  ↓
coding-agent                              ← 最后
```

`build:offline` 是同一顺序，但 `ai` 用 `build:offline`（不刷新模型数据）。这对 CI/无网络环境很重要。

## 2. `npm run check`：提交前的总闸

```json
"check": "biome check --write --error-on-warnings . &&
          npm run check:pinned-deps &&
          npm run check:runtime-deps &&
          npm run check:ts-imports &&
          npm run check:entry-graphs &&
          npm run check:install-lock:coding-agent &&
          tsc --noEmit &&
          npm run check:browser-smoke"
```

逐项看：

| 步骤 | 脚本 | 检查什么 |
|---|---|---|
| 格式 + lint | `biome check` | 格式、lint、导入顺序（`--error-on-warnings`：警告也算错） |
| 依赖钉版本 | `check-pinned-deps.mjs` | 直接外部依赖必须是精确版本 |
| 运行时依赖 | `check-runtime-deps.mjs` | 包声明的依赖与实际 import 一致（不多不少） |
| TS 相对导入 | `check-ts-relative-imports.mjs` | 相对 import 必须带 `.ts` 后缀 / 符合 Node strip-types |
| 入口图 | `check-entry-graphs.mjs` | 打包入口的依赖图没有意外（体积/循环） |
| 安装锁 | `generate-coding-agent-install-lock.mjs --check` | install-lock 与根 lockfile 一致 |
| 类型 | `tsc --noEmit` | 全仓类型检查 |
| 浏览器 smoke | `check-browser-smoke.mjs` | 确认 `ai` 等包在浏览器环境能被打包/运行 |

**这套 check 的设计理念**：把所有「靠人记住的约定」变成脚本。钉版本、import 后缀、入口图——这些在 code review 里容易漏的东西，都自动化了。

## 3. 测试：三层

### ① 单元/集成测试

```bash
./test.sh              # 从仓库根，跑所有非 e2e 测试
```

`test.sh` 第一段值得一读：它**完全隔离环境**——

```bash
test_env=(
  "PATH=$PATH" "HOME=$test_root/home" "TMPDIR=$test_root/tmp"
  "XDG_CONFIG_HOME=$test_root/home/.config"
  "GIT_CONFIG_NOSYSTEM=1" "GIT_CONFIG_GLOBAL=/dev/null"
  "GIT_TERMINAL_PROMPT=0" "GIT_ASKPASS=$git_askpass"
  "NPM_CONFIG_USERCONFIG=$test_root/npm-userconfig"
  ...
)
```

还有一段防御性清理逻辑（只删带 `.pi-test-owned` 标记的目录、拒绝删除软链接、校验路径前缀）。

**为什么要这么做**：pi 会读写 `~/.pi`、会跑 git 命令、会调 npm。测试如果不隔离，就会污染开发者的真实配置，甚至误删东西。这是「一个会操作系统的东西」必须付出的测试基础设施成本。

`AGENTS.md` 的测试规则也很严格：

> Never run the full vitest suite directly: it includes e2e tests that activate when endpoint/auth env vars are present. For all non-e2e tests, run `./test.sh`.

也就是说：**环境里有 API key 时直接跑 vitest 会意外产生真实调用**。所以统一入口是 `test.sh`。

### ② 包内测试

```bash
node "$(git rev-parse --show-toplevel)/node_modules/vitest/dist/cli.js" --run test/specific.test.ts   # vitest 包
node --test test/specific.test.ts                                                                   # tui（node:test）
```

`coding-agent/test/suite/` 有专门的规则：

> use `test/suite/harness.ts` + the faux provider. No real provider APIs, keys, or paid tokens.

`providers/faux.ts` 就是假 provider——**测试不花钱、不出网、可确定性重放**。

### ③ 行为评测（`packages/evals`）

> Behavioral evals for Pi's coding agent, built with `vitest-evals`.

两类：

| 文件 | 类型 | 做什么 |
|---|---|---|
| `*.docs.eval.ts` | documentation-lift eval | 在「有文档 / 无文档」两个隔离容器里跑同一批 case，报告**提升幅度** |
| 其他 `*.eval.ts` | host eval | 普通 vitest-evals 套件 |

```bash
PI_PROVIDER=openai-codex PI_MODEL=gpt-5.6-sol npm run eval -w packages/evals
```

**「文档提升度」评测是个很有想法的设计**：它回答的不是「agent 好不好」，而是「**这份文档对 agent 有没有用**」。对一个以 `AGENTS.md`/docs 驱动行为的工具，这是核心指标。runner 结构（`cli.ts` / `docker.ts` / `plan.ts` / `report.ts`）显示它会：

1. 构建两个镜像（有/无文档）；
2. 把 case 展开成 `(case, variant, repetition)`；
3. 在隔离容器里跑；
4. 读 Vitest JSON，配对两组，算 lift。

## 4. 提交门禁：husky pre-commit

`.husky/pre-commit`：

1. `check-lockfile-commit.mjs` —— 阻止意外提交 lockfile（除非 `PI_ALLOW_LOCKFILE_CHANGE=1`）；
2. `npm run check` —— 全套检查；
3. 如果改动了 `packages/ai/*`、`package.json`、`package-lock.json` → 额外跑 `check:browser-smoke`；
4. 把格式化后又被暂存的文件重新 `git add`（因为 biome `--write` 会改文件）。

第 4 步是个细节但很重要：**格式化修改了文件，如果不重新 add，提交的内容就没格式化**。

## 5. CI（`.github/workflows/`）

13 个 workflow，按职责分：

| Workflow | 作用 |
|---|---|
| `ci.yml` | 主流程：install → build → check → build daemon → test；外加 mcp-conformance |
| `build-binaries.yml` | 打各平台单文件二进制；tag 时发布 npm |
| `nix.yml` | Nix flake 构建（Linux/macOS），成功后快进 `stable` 分支 |
| `env.yml` / `env-daemons.yml` | `pi-env` Rust daemon 的构建与测试 |
| `npm-audit.yml` | 定时 `npm audit --omit=dev` + `audit signatures` |
| `publish-model-catalog.yml` | 发布模型目录（pi.dev） |
| `issue-gate.yml` / `issue-analysis.yml` / `issue-triage-labels.yml` / `approve-contributor.yml` | 社区流程自动化（新贡献者 PR 默认自动关闭，维护者每日复审） |
| `pr-gate.yml` | PR 门禁 |
| `remove-inprogress-on-close.yml` | 清理 |

`ci.yml` 的细节：

```yaml
- run: sudo apt-get install -y libcairo2-dev libpango1.0-dev ... fd-find ripgrep
- run: npm ci --ignore-scripts
- run: npm run build
- run: npm run check
- run: npm run build:daemon --workspace packages/env
- run: npm test
```

- 装 `fd`/`rg`：因为 `find`/`grep` 工具有两种后端；
- `--ignore-scripts`：**不跑生命周期脚本**（供应链加固）；
- 先 build 再 check（类型检查需要构建产物的声明文件）。

## 6. 供应链加固（README 有专章）

这是这个仓库最严肃的部分之一：

| 措施 | 实现 |
|---|---|
| 直接依赖钉死精确版本 | `.npmrc` `save-exact=true` |
| 避免当天发布的依赖 | `.npmrc` `min-release-age=2` |
| lockfile 是唯一真相 | pre-commit 阻止意外提交 |
| 校验钉版本 | `check:pinned-deps` |
| install-lock（给 pi.dev 安装器） | `generate-coding-agent-install-lock.mjs` + allowlist |
| 生命周期脚本需审查 | install-lock 生成的 allowlist，新依赖默认失败 |
| 发布冒烟测试 | `npm run release:local`（在仓库外做隔离安装） |
| 定时审计 | `npm-audit.yml`（含签名验证） |

`AGENTS.md` 对 `undici` 更新还有一条特别规定：**必须先读 changelog 评估影响**。这是一个被现实教育过的团队才会写的规则。

## 7. 发布流程（`.pi/skills/release.md` 是一份完整的 runbook）

关键点：

1. **Lockstep 版本**：所有包共享同一个版本号，一起发。
   `patch` = 修复 + 新增，`minor` = 破坏性变更，**没有 major**。
2. **先跑 `/cl`**：审计并更新每个包的 `[Unreleased]` changelog。
3. **本地冒烟**：`npm run release:local` 在 `/tmp` 里做隔离安装，Node 与 Bun 两种产物都要测：`--help`、`--version`、`--list-models`、`-p "Say exactly: ok"`、交互模式（用 tmux）。
4. **`npm run release:patch`**：刷新 Nix 模型目录钉、bump 版本、更新 changelog、重建产物、跑 check、提交 `Release vX.Y.Z`、打 tag、加下一轮 `[Unreleased]` 段、推 main + tag。
5. **CI 发布 npm**：tag 触发 `build-binaries.yml`，用 **npm trusted publishing（OIDC）**，不需要本地 `npm publish`/OTP。发布后 `announce-pi-dev-release` 校验每个包都能在精确版本解析到，再写 R2 标记。
6. **CI 构建 Nix**：tag 触发 `nix.yml`，成功后快进 `stable` 分支。
7. **失败恢复**：publish helper 幂等（跳过已存在的版本），重跑失败的 job，**绝不重跑 `release:patch`**。

**注意 5 里的顺序约束**：`pi.dev/api/latest-version` 读的是 R2 标记，而标记只在「所有包都可解析」后才写。这保证了「宣布的版本一定装得上」。

## 8. 依赖与运行时约束（会影响你写代码）

- **只允许可擦除 TS 语法**（无 `enum`、`namespace`、参数属性、`import =`、`export =`）——因为 Node 22 直接 strip types 运行；
- **禁止 inline import**（`await import()` 动态类型导入）——`AGENTS.md` 明确禁止；
- **不用 `any`**（除非必要）；
- **不改 `models.generated.ts`**，改生成器；
- **coding-agent 里资源路径必须走 `config.ts` 的 helper**，不能 `__dirname`；
- **键绑定不能硬编码**，加到 `DEFAULT_EDITOR_KEYBINDINGS` / `DEFAULT_APP_KEYBINDINGS`。

这些规则每一条都对应过现实中的一个坑。

## 9. 开发脚本快速参考

```bash
npm install --ignore-scripts     # 装依赖（不跑生命周期脚本）
npm run build                    # 刷新模型数据 + 构建所有包
npm run build:offline            # 无网络构建
npm run check                    # lint + 格式 + 类型 + 各种校验
./test.sh                        # 跑非 e2e 测试（隔离环境）
./pi-test.sh                     # 从源码跑 pi（任意目录可用）
npm run check:package-install    # 用消费者视角验证 npm 包装得上
npm run profile:tui / profile:rpc  # 性能分析
npm run generate:models          # 重新生成模型清单
```

`scripts/` 下 40+ 脚本的分组：

- **依赖/供应链**：`check-pinned-deps`、`check-runtime-deps`、`generate-coding-agent-install-lock`、`npm-audit`
- **模型数据**：`generate-models`、`hydrate-model-catalog`、`diff-model-catalog`、`publish-model-catalog`
- **发布**：`release.mjs`、`local-release.mjs`、`publish.mjs`、`release-notes.mjs`、`build-binaries.sh`
- **性能/统计**：`profile-coding-agent-node.mjs`、`tool-stats.ts`、`session-context-stats.mjs`、`cost.ts`
- **构建校验**：`check-entry-graphs`、`check-browser-smoke`、`check-ts-relative-imports`

## 10. 本章要点

- 构建按拓扑序；`build:offline` 支持无网络。
- `npm run check` 把「靠记忆的约定」全部脚本化（钉版本、import 后缀、入口图、install-lock）。
- 测试三层：隔离环境单元测试（`test.sh`）、包内测试（faux provider）、行为评测（含文档提升度）。
- pre-commit 阻断 lockfile 意外提交，并在格式化后重新 stage。
- 发布是 lockstep + 本地冒烟 + OIDC 发布 + Nix stable 快进，且**宣布晚于可安装**。
- 代码规则（可擦除语法、no inline import、资源路径 helper、可配置键绑定）都对应真实坑。
