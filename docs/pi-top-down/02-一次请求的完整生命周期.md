# 02 一次请求的完整生命周期

这一章是一条「黄金线索」：在 pi 里输入 `帮我修一下这个 bug` 然后回车，到屏幕上出现回复，中间发生了什么。后面每一章都是这条线索上某一段的放大。

## 0. 全景时序

```
用户输入
  │
  ├─ [TUI] Editor.onSubmit → InteractiveMode 处理输入（斜杠命令？@文件？!shell？）
  │
  ├─ [AgentSession] prompt(text)
  │     ├─ 展开 prompt template
  │     ├─ 组装附件（图片/文件/粘贴/shell 输出）
  │     └─ 持久化 user message 到 session JSONL
  │
  ├─ [Agent] prompt() → 启动一次 run
  │     │
  │     ├─ agent_start 事件
  │     └─ agentLoop()  ← packages/agent/src/agent-loop.ts
  │            │
  │            ├─ turn_start
  │            ├─ prepareNextTurn（压缩/换模型等准备工作）
  │            ├─ 注入 pending 消息（steering / follow-up / system 补丁）
  │            ├─ prepareRequest（装入权威上下文）
  │            ├─ streamAssistantResponse()
  │            │     ├─ transformContext(AgentMessage[])
  │            │     ├─ convertToLlm(AgentMessage[]) → Message[]
  │            │     ├─ getApiKey(provider)   ← 可能是会过期的 OAuth token
  │            │     └─ streamFn(model, ctx, opts)  ← ai 包
  │            │            └─ Models.streamSimple → provider → api 实现
  │            │                   └─ SSE/WebSocket 解析 → AssistantMessageEvent*
  │            │
  │            ├─ message_start / message_update* / message_end
  │            ├─ 有 toolCall？
  │            │     ├─ prepareToolCall（参数校验 + beforeToolCall）
  │            │     ├─ execute（并行或串行）
  │            │     ├─ afterToolCall → finalize
  │            │     ├─ tool_execution_start/update/end
  │            │     └─ toolResult message_start/end
  │            ├─ finishTurn（决定 continue / end / 默认）
  │            ├─ turn_end
  │            └─ 还有工具调用 / steering / follow-up → 下一轮 turn
  │
  ├─ agent_end
  └─ [AgentSession] 落盘、统计 token、更新 UI
```

## 1. 第一站：输入怎么变成一条消息

`main.ts` 只负责把 CLI 参数翻译成 `CreateAgentSessionOptions`，然后交给 `createAgentSession()`。真正的运行期入口是 `AgentSession`。

输入在进入 agent 之前会被 `AgentSession` 加工：

- **斜杠命令**（`/login`、`/compact`、`/model`…）在这里被截获，不会送到模型；
- **prompt template** 在 `expandPromptTemplate()` 里展开；
- **`@file`、粘贴文本、图片、`!shell`** 变成 message content 的附加块；
- 处理完才变成 `AgentMessage`，**并且先写进会话文件**（这是 pi 的一个原则：能回溯）。

## 2. 第二站：Agent 启动一次 run

`Agent.prompt()` 做三件事：把消息压进 steering/直接上下文、创建 `AbortController`、跑 `agentLoop()`。

`Agent` 自己不实现循环，它是一层「带状态和队列的门面」：

- 持有 `AgentState`（model / thinkingLevel / tools / messages / isStreaming…）；
- 持有两个队列 `steeringQueue` / `followUpQueue`；
- 把循环抛出的每个 `AgentEvent` **按注册顺序 await** 分发给订阅者（`subscribe`）。

## 3. 第三站：循环内的四个「插入点」

`runLoop()` 里每一轮 turn 都会按固定顺序经过四个回调，这是整个运行时最重要的扩展设计：

| 顺序 | 回调 | 用途 |
|---|---|---|
| 1 | `prepareNextTurn` | 上一轮结束后、下一轮开始前：可能要压缩上下文、切模型、注入消息 |
| 2 | `prepareRequest` | 每次请求前（含第一次）：装入「权威持久化上下文」，例如从会话文件重建 |
| 3 | `streamFn` | 真正调模型；契约是**不抛异常**，错误编码进流里（`stopReason: "error"`） |
| 4 | `finishTurn` | 一轮（assistant + 所有工具结果）结束后，在 `turn_end` 之前决定 `continue` / `end` |

`prepareRequest` 在 `agent-loop.ts` 里的调用点：

```ts
const requestUpdate = await config.prepareRequest?.(
  { context: currentContext, model: config.model, thinkingLevel: config.reasoning ?? "off" },
  signal,
);
if (requestUpdate) {
  currentContext = requestUpdate.context ?? currentContext;
  config = { ...config, model: ..., reasoning: ... };
}
```

**为什么需要它**：UI 层可能往 agent 内存里塞了一堆「只给界面看」的消息、或者做了临时裁剪；真正要发给模型的历史，真相在会话文件里。`prepareRequest` 让上层有机会在最后一刻把权威上下文换进去。

## 4. 第四站：请求如何变成流

`streamAssistantResponse()` 是整个循环里最关键的 60 行：

```ts
let messages = context.messages;
if (config.transformContext) messages = await config.transformContext(messages, signal);
const llmMessages = await config.convertToLlm(messages);
const llmContext = normalizeContext({ messages: llmMessages });
const resolvedApiKey =
  (config.getApiKey ? await config.getApiKey(config.model.provider) : undefined) || config.apiKey;
const response = await streamFunction(config.model, llmContext, { ...config, apiKey: resolvedApiKey, signal });
```

两个数据转换是 pi 的类型核心：

```
AgentMessage[]  --transformContext-->  AgentMessage[]  --convertToLlm-->  Message[]
（可以含自定义角色）                    （裁剪/注入）                        （只有 4 种角色）
```

然后遍历事件流：`start` 时把「部分消息」放进 context 并发 `message_start`；每个 delta 更新最后一条并发 `message_update`；`done`/`error` 时替换成最终消息并发 `message_end`。

> 细节：`partialMessage` 是**原地替换** context 数组的最后一项。所以 UI 拿到的 `message_update` 里的 `message` 是浅拷贝快照，避免渲染层读到一半被改。

## 5. 第五站：工具调用

assistant 消息里 `content` 出现 `{ type: "toolCall" }` 就进入工具执行。两个特殊情况：

1. **`stopReason === "length"`**：输出被 token 上限截断，工具参数可能是「能解析但残缺」的 JSON。pi 的选择是**整批失败**（`failToolCallsFromTruncatedMessage`），让模型重发，而不是执行一个参数残缺的 `rm`。
2. **并行模式**：先串行做「准备」（校验参数 + `beforeToolCall`），再把允许执行的工具并发跑；`tool_execution_end` 按完成顺序发，但 toolResult 消息按 assistant 源顺序落盘。

## 6. 第六站：一轮结束，谁决定继续

`finishTurn` 返回 `{action:"continue"}` 时会保证「还有一次请求」；但如果有工具结果、steering、follow-up 已经会触发请求，这个决定就被它们满足，不会多打一次模型。

内层循环的继续条件写得很朴素：

```ts
while (hasMoreToolCalls || pendingMessages.length > 0) { ... }
// 内层结束后检查 follow-up，没有就退出
```

外层循环专门处理「本来要停了，但 follow-up 队列里还有东西」。

## 7. 第七站：事件到达 UI

`AgentEvent` 是 UI 的唯一输入源：

```
agent_start → turn_start → message_* → tool_execution_* → turn_end → … → agent_end
```

`InteractiveMode` 把这些事件映射成组件更新；`print-mode` 只取最后的文本；RPC 模式把它们序列化成 JSONL。**同一个事件流，三种消费方式**（第 19 章）。

## 8. 时序里的三个「反直觉点」

1. **`agent_end` 不是结束**：pi 规定 `agent_end` 是最后一个事件，但**await 的订阅者仍然计入本次 run**。所以「落盘完成」可以放在 `agent_end` 监听器里，`await agent.prompt()` 会等它。
2. **工具不是「LLM 说完就执行」**：中间有参数校验、`beforeToolCall`（可 block）、`afterToolCall`（可改结果）、terminate 判定。
3. **模型切换是运行时状态**：`prepareNextTurn` 可以改 `config.model`，同一 run 内不同 turn 用不同模型是合法的。

## 9. 本章要点

- 一条消息的旅程：TUI → AgentSession（加工+落盘）→ Agent → 循环 → streamFn → ai → provider → 网络。
- 四个插入点（`prepareNextTurn` / `prepareRequest` / `streamFn` / `finishTurn`）是 pi 可扩展性的地基。
- 两次转换（`transformContext` / `convertToLlm`）是所有上下文管理的必经关卡。
- 一切可观察行为都是 `AgentEvent`，UI 只是消费者。
