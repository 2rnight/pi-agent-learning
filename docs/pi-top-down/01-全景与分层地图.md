# 01 全景与分层地图

## 1. 这个仓库到底解决什么问题

一个「编码代理」需要同时解决四件事，Pi 把它们拆给了不同的包：

| 问题 | 答案在哪个包 | 典型代码 |
|---|---|---|
| 怎么和几十家模型供应商说话？ | `pi-ai` | `createModels()` / `provider.stream()` |
| 怎么让模型「调工具」并循环下去？ | `pi-agent-core` | `agentLoop()` / `Agent` |
| 怎么变成一个能用的编码 CLI？ | `pi-coding-agent` | `main.ts` / `AgentSession` |
| 怎么在终端里画界面？ | `pi-tui` | `TuiMainScreen` / 组件树 |

再加一层横向能力：`mcp`（接外部工具协议）、`codemode`（让模型写代码编排工具）、`telemetry`（遥测）。

## 2. 依赖倒置的方向

注意依赖是**单向向下**的：

```
coding-agent  ──►  agent-core  ──►  ai  ──►  telemetry
      │
      ├──► tui          (纯 UI 库，零内部依赖)
      ├──► mcp          (纯协议客户端，零内部依赖)
      ├──► codemode     (纯沙箱，零内部依赖)
      └──► chord        (chord 自身零内部依赖)
```

`ai` 不知道 `agent` 存在，`agent` 不知道 `coding-agent` 存在。这是理解整个仓库最重要的一条约束：**每一层都能被单独使用**。`packages/agent/README.md` 的 Quick Start 就是「只用 agent-core + ai 写一个 20 行的 agent」；`packages/durable` 则完全绕开 `agent-core`，自己实现了持久化循环。

## 3. 包的分组方式

按「谁依赖谁」可以分成三簇：

### 簇 A：Pi 产品栈

- `telemetry`：只有 6 个文件，定义 `TelemetryContext` / `TelemetrySpan` 回调契约 + 内存实现 + 一致性测试。**没有导出器**，故意做成厂商中立。
- `ai`：194 个源文件、26k 行。内部再分 `api/`（协议实现）、`providers/`（厂商工厂）、`auth/`（凭证）、`models.ts`（注册表）。
- `agent`：只有 6 个文件、2.5k 行。**小而关键**——核心循环 `agent-loop.ts` 940 行，`agent.ts` 613 行，类型 529 行。
- `coding-agent`：299 个文件、85k 行。产品复杂度集中在这里（`interactive-mode.ts` 单文件 7072 行）。
- `tui`：45 个文件、19k 行，含 Windows/macOS/Linux 原生模块（剪贴板等）。

### 簇 B：Chord 实验栈

- `chord`：29 个文件、8.8k 行。**声明自己不是 Pi 包**：「it does not depend on any other Pi workspace package and can be used by unrelated applications」。
- 派生：`protocol`（CBOR 信封）、`client`、`server`、`durable`（19.5k 行）、`env`（TS 客户端 + Rust daemon）。

### 簇 C：开发/评测

- `evals`（private）：用 `vitest-evals` 做行为评测，包括「文档有效性」对照实验（有文档 vs 无文档的跑分差）。

## 4. 三个入口，看清楚就不迷路

读代码时永远从这三个文件开始：

1. **`packages/coding-agent/src/main.ts`**（998 行）——CLI 真正的 main。它做参数解析，然后翻译成 `createAgentSession()` 的选项。文件头注释写得很直白：*"This file handles CLI argument parsing and translates them into createAgentSession() options. The SDK does the heavy lifting."*
2. **`packages/coding-agent/src/core/sdk.ts`** —— `createAgentSession()`，组装 settings、model runtime、tools、extensions、session manager。
3. **`packages/agent/src/agent-loop.ts`** —— 一切「agent 感」的来源：循环、工具、事件。

## 5. 规模与复杂度分布（决定你该读多深）

```
coding-agent   ████████████████████████████████████  85k
ai             ███████████                           26k
durable        ████████                              20k
tui            ████████                              19k
chord          ████                                   9k
agent          █                                      2.5k   ← 性价比最高的阅读目标
mcp            █                                      3.2k
server/client/protocol/codemode/env/telemetry         6k
```

**阅读建议**：`agent` 的 2.5k 行读透了，`coding-agent` 的 85k 行就只是「在它外面加 IO、加持久化、加 UI、加扩展」。反过来先读 `coding-agent` 会被 7072 行的交互模式淹没。

## 6. 仓库自我托管（一个有意思的信号）

仓库根目录有 `.pi/`：

```
.pi/prompts/{cl,deslop,is,pr,sa,wr}.md   # 团队自己的斜杠命令
.pi/skills/{add-llm-provider,release,interactive-testing}.md
.pi/extensions/{tps,redraws,import-repro,prompt-url-widget}.ts
```

这就是 pi 跑在 pi 自己仓库上的配置。`AGENTS.md` 既是「给人类贡献者」的规则，也是 pi 启动时读进系统提示词的项目上下文——**它同时是文档和运行时输入**。这一点在第 15 章会展开。

## 7. 本章要点

- 依赖严格单向，每层可独立使用；`agent-core` 只有 2.5k 行，是理解全局的杠杆点。
- 仓库有两条产品线，别把 `chord` 那套当成 pi CLI 的一部分。
- 复杂度不在「算法」而在「集成」：85k 行的 coding-agent 大部分是模式、扩展、资源、UI 的接线。
- 入口是 `main.ts → sdk.ts → AgentSession → Agent → agentLoop`。
