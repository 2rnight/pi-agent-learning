# 03 工具沙箱与语义路由

这两件事被放在一个需求里，但难度相差一个数量级：**语义路由是「接口已留、填空即可」，沙箱是「安全产品、验收最难」**。

---

## A. 语义路由（难度 ★★☆☆☆）

### A.1 二开前：工具是怎么进上下文的

```
① 工具注册
   builtInExtensions / 扩展 → pi.registerTool({ ... , defaultActive })
   → ToolDefinition（带 renderCall/renderResult、ToolExposure、namespace）

② 变为可执行
   wrapRegisteredTools() → AgentTool[]
   → agent.state.tools

③ 告诉模型
   agent-loop 的 declareToolChanges(context, pending)
   → 差量写进 system message 的 toolsAdded / toolsRemoved
   → 模型看到的工具集 = 转录里声明的累积结果

④ 调用
   模型发 toolCall → prepareToolCall → execute
```

**关键事实**：**所有 `direct` 暴露的工具都会进系统提示词**（名字 + 描述 + JSON Schema）。工具越多，上下文越贵。

### A.2 二开前：`tool_search` 已经做了什么

`packages/coding-agent/src/extensions/tool-search/tool.ts` 的注释直接给出了定位：

> Tool discovery: a **BM25 ranker** over tool metadata, shared by `searchTools()` in codemode scripts and the optional `tool_search` tool.
> `tool_search` searches tools that are **not declared to the model** (`codemode` and `deferred` exposure) and loads the matches, so they are declared for the next model call.

也就是说：

- 存在两档工具：**已声明**（进上下文）与 **未声明**（不进上下文）；
- 未声明的可以按需 `tool_search` 加载；
- 加载后会**写进转录**（"survives `/tree`, resume, and fork"）；
- 排序器有**显式接口**：

```ts
/** Ranks tools for a query. BM25 today; a hybrid ranker with embeddings can replace it. */
export interface ToolRanker {
  rank(query: string, documents: readonly ToolSearchDocument[], limit: number): ToolSearchMatch[];
}
```

**这句话就是需求第 3 项后半段的实现说明。** 它甚至预告了要做的事："a hybrid ranker with embeddings"。

### A.3 差距 & 指标校准（重要）

| 项 | 现状 | 差距 |
|---|---|---|
| 排序器接口 | 已有 `ToolRanker` | 无，只需实现 |
| 语义（embedding）排序 | 无，纯 BM25 | 需要 embedding + 混合排序 |
| 预过滤（进请求前就砍） | 部分（靠 `ToolExposure` 手工标注） | 需要按语义自动决定哪些进 `direct` |
| 检索耗时 | **内存 BM25，微秒级** | — |

**「候选工具检索耗时降低 60%」这个指标本身站不住**：现在检索就是一次内存 BM25，换成向量只会更慢（要算 query embedding + 向量搜索）。真正该测的是：

1. **工具声明占用的上下文 token**：200 个工具 ≈ 每个 100–200 token ≈ 2–4 万 token。降到 8 个 ≈ 1000 token。**这才是 60%+ 的真实来源。**
2. **首 token 延迟**（prompt 变短 → 首 token 更快）。
3. **工具选择准确率**（防止为了省 token 把正确工具过滤掉）。

### A.4 二开思路

```ts
// packages/coding-agent/src/extensions/tool-search/ 下新增 hybrid-ranker.ts

const hybridRanker: ToolRanker = {
  rank(query, documents, limit) {
    // ① 先跑既有 BM25（快、免费、可解释）
    const lexical = bm25.rank(query, documents, limit * 3);
    // ② 只在 BM25 置信度低时才走向量（省钱）
    if (lexical.length >= limit && lexical[limit - 1].score > LEXICAL_CONFIDENT) {
      return lexical.slice(0, limit);
    }
    // ③ 混合：RRF（reciprocal rank fusion）合并两路
    const semantic = vector.rank(query, documents, limit * 3);
    return rrf([lexical, semantic]).slice(0, limit);
  },
};
```

三个工程要点：

1. **不是「换成向量」，而是「混合 + 分级」**：BM25 命中明确时根本不调 embedding（省延迟省钱）。
2. **`documents` 的构建要改**：`createToolSearchDocument()` 现在拼 name + description，要加上 **参数名与工具标签**（模型搜索时用的词经常是参数名，如 "offset"、"encoding"）。
3. **embedding 要预计算并缓存**：工具集在会话期间基本不变，工具文档的 embedding 应缓存在内存/磁盘，只有 query 每次算。

### A.5 二开后流程

```
启动/扩展变更
  → 工具清单变化 → 重算工具文档 embedding（缓存，异步）

会话首轮
  → 按 settings 决定 direct 预算（默认 8–12 个）
  → 对"常驻工具"（read/bash/edit/write）直接 direct
  → 其余进入 deferred

模型需要别的工具
  → 调 tool_search("导出 csv")
  → hybrid ranker: BM25 → (必要时 embedding) → RRF
  → 命中的工具 setActiveTools() → 下一轮请求的工具集变化
  → declareToolChanges 写 toolsAdded（进转录，可回放）

【新】可选：预测式预加载
  → 用本轮用户消息 + 最近工具调用历史，预先加载 top-3 高概率工具
  → 避免"模型先搜一次再调用"的额外往返
```

### A.6 工作量与验收

| 项 | 人日 |
|---|---|
| 工具文档增强（含参数、标签） | 1 |
| BM25 → 混合排序（RRF） | 1.5 |
| embedding 缓存 + 服务接入 | 1.5 |
| 预算策略 + 预测式预加载 | 1 |
| 测试与指标埋点 | 1 |
| **合计** | **3–5** |

验收：`direct` 工具数、工具声明 token 数、首 token 延迟、工具选择准确率（用固定测试集人工标注）。

## B. 工具沙箱（难度 ★★★★☆）

### B.1 二开前：已经有什么（比预期多）

`packages/codemode` 的隔离其实已经做得不错，`runtime/host.ts`：

```ts
import { Worker } from "node:worker_threads";
// One script run in its own worker and QuickJS VM. A fresh worker per run keeps ...
worker = new Worker(options.workerUrl, { workerData });
```

现有隔离层级：

| 层 | 现状 |
|---|---|
| **语言沙箱** | QuickJS 编译到 WASM，不是 Node 上下文 |
| **线程隔离** | `worker_threads`，每次执行一个新 worker |
| **能力白名单** | 只有 `tools` / `ALL_TOOLS` / `text` / `image` / `exit` / `store` / `load` |
| **无网络无定时器** | 无 `fetch`、无 `setTimeout`、无 `require`、无模块、无 `WebAssembly` |
| **超时** | `timeoutMs`，`Infinity` 时仍可被 signal 中断 |
| **内存** | `memoryLimitBytes`，超出 → `InternalError: out of memory` |
| **死锁检测** | 等一个永远不会 settle 的 promise → 立即失败 |
| **持久化事务** | 失败执行不产生 `storeWrites` |

**所以「已有沙箱」，缺的是「沙箱与宿主文件系统的边界」，以及「不依赖 QuickJS 的通用脚本执行」。**

### B.2 需求里的「AST 语法树 + 子进程隔离」要拆开看

| 手段 | 能解决的 | **不能**解决的 |
|---|---|---|
| AST 静态分析 | 检测 `while(1)` 字面量、禁用 API 引用、可疑 import | 运行时构造的死循环、内存炸弹、逻辑越权 |
| 子进程隔离 | 崩溃不拖垮宿主、可 kill | 文件系统仍可写（同用户权限） |
| 资源限制 | CPU/内存/进程数 | 路径越权 |
| 容器/seccomp | 真正的边界 | 部署复杂 |

**核心判断：AST 只能当「预检与提示」，绝不可作为安全边界。** 任何「AST 通过了所以安全」的实现都会在上线三个月内被绕过。

真正的边界是：**进程隔离 + 资源限制 + 工作目录 chroot 式约束 + 路径白名单**。

### B.3 正确的分层设计

```
┌──────────────────────────────────────────────────────┐
│ L4 策略层：谁能跑什么                                  │
│   项目信任（已有 project_trust）、工具级 allow/deny、   │
│   扩展 `tool_call` 事件拦截（已有）                    │
├──────────────────────────────────────────────────────┤
│ L3 静态预检（新增，AST）                               │
│   拒绝明显危险的构造 / 提示可疑用法 / 计算复杂度上限     │
│   ⚠ 只做"早失败与提示"，不做"准入判定"                │
├──────────────────────────────────────────────────────┤
│ L2 运行时隔离（新增，子进程）                          │
│   child_process.fork 独立进程 + --max-old-space-size   │
│   + 无网（unshare/网络命名空间或环境变量层禁用）        │
│   + 工作目录限定 + 路径白名单（realpath 后校验）        │
│   + 超时 kill（SIGKILL 兜底）                          │
├──────────────────────────────────────────────────────┤
│ L1 能力层（已有）                                      │
│   只有注入的工具，没有 fs / net / 模块系统              │
└──────────────────────────────────────────────────────┘
```

### B.4 二开前 vs 二开后的执行流程

**二开前（codemode 脚本）**

```
模型调 codemode 工具
  → CodemodeSandbox.execute(code, {tools, timeoutMs, memoryLimitBytes})
  → spawn worker_threads Worker（每次新 worker）
  → 加载 QuickJS WASM
  → 注入 tools（调回宿主走 runToolCall → beforeToolCall/afterToolCall 生效）
  → 脚本跑完 / 超时 / 死锁 → 收集 output/value/storeWrites
  → 结果作为 toolResult 返回模型
```

**二开前（普通工具，如 `bash`）——注意这里没有沙箱**

```
模型调 bash 工具
  → createLocalBashOperations()
  → 直接 spawn shell，继承 Pi 进程的用户权限
  → 可读 ~/.ssh、可写任意路径、可访问网络
```

`README.md` 对此说得很直白：

> Pi does not include a built-in permission system for restricting filesystem, process, network, or credential access.

配套方案是**容器化**（`docs/containerization.md` 的 Gondolin / Docker / OpenShell 三种模式），靠 `BashOperations` / `ReadOperations` 这类抽象把工具路由进沙箱。

**二开后**

```
模型调工具
  → L4 策略检查（项目信任 / 扩展 tool_call 事件 / 工具白名单）
  → 分流：
     ├─ 只读工具（read/grep/find/ls）→ 路径白名单校验 → 直接执行（低开销）
     ├─ 写工具（edit/write）        → 路径白名单 + 互斥队列（已有 file-mutation-queue）
     └─ 执行类（bash / codemode）
          → L3 AST 预检（快速失败 + 计分）
          → L2 子进程沙箱：
               fork 子进程（独立资源上限）
               工作目录限定 + 路径 realpath 校验
               禁用网络 / 只读挂载（按配置）
               超时 → SIGTERM → SIGKILL
             → 结果回传（stdout/stderr/exit code，走既有 truncate 限额）
  → toolResult（isError 明确，错误码可区分"策略拒绝"与"执行失败"）
```

### B.5 为什么「子进程」比「worker_threads」更适合做边界

| | `worker_threads`（现状） | `child_process`（建议） |
|---|---|---|
| 内存上限 | 共享进程堆上限，难精确 | `--max-old-space-size` 精确 |
| 崩溃隔离 | 同进程，OOM 可能拖垮宿主 | 完全隔离 |
| 强制终止 | 只能 `terminate()`，同步 JIT 循环可能无效 | `SIGKILL` 必定生效 |
| 系统调用限制 | 与宿主相同 | 可配合 seccomp / 命名空间 |
| 开销 | 低（~10ms） | 略高（~30–50ms） |

**结论**：codemode 的 QuickJS + worker 组合已经是很好的「语言级」沙箱，**不要在它上面重造**；需要新增的是「通用脚本/命令执行」的**进程级**沙箱，并把它接进 `BashOperations` / `Operations` 抽象（这个抽象已经为容器化预留，见第 14 章）。

### B.6 工作量与验收

| 项 | 人日 |
|---|---|
| 子进程沙箱运行时（fork + 资源限制 + kill 链） | 4 |
| 路径白名单（realpath、符号链接、跨平台） | 3 |
| AST 预检（解析、规则集、误报调优） | 3 |
| 接入 `Operations` 抽象（read/write/bash/codemode） | 2 |
| 策略配置 + 策略拒绝的错误码 | 1 |
| 安全测试（逃逸用例集） | 3 |
| **合计** | **10–15** |

### 验收（安全项的标准写法）

不要写"安全"。写**逃逸用例集**，每条都要有测试：

1. `while(true){}` → 超时被杀，宿主存活
2. 分配 4GB 数组 → OOM 失败，宿主存活
3. `require('fs')` / `import('fs')` → 不可用
4. `fetch('http://...')` → 不可用（网络禁用）
5. 读 `~/.ssh/id_rsa` → 路径白名单拒绝
6. `../../../etc/passwd` → realpath 后拒绝
7. 符号链接指向白名单外 → 拒绝
8. `process.exit()` / `process.kill(ppid)` → 无效或仅终止自身
9. 原型链污染尝试（`Object.prototype.x = 1`）→ 不影响宿主（QuickJS 天然隔离）
10. 子进程 fork 炸弹 → 进程数上限

## C. 两件事的顺序建议

```
第 1 周  语义路由（3a）      ← 收益立竿见影、风险低
第 4 周  子进程沙箱骨架      ← 先做"执行类工具的进程隔离"
第 5 周  路径白名单 + 逃逸测试
第 6 周  AST 预检            ← 最后做，且只当预检
```

**AST 放最后**，因为它对安全贡献最小、维护成本最高（语言演进、规则误报），但它是唯一能提供「友好报错」的手段——所以它是有价值的**体验**改进，不是**安全**改进。把它当安全功能做，会得到一个既慢又漏的系统。
