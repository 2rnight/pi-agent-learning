# 02 分层记忆系统：Redis 短期 + 向量长期 + 用户画像

> 这是四项里**代码不难、设计最难**的一项。本文件一半篇幅在讲「该不该做、做到什么范围」。

## 一、二开前：今天 pi 的记忆是怎么工作的

pi 其实已经有一套相当完整的记忆分层，只是它不是 Redis + 向量库。

### 1.1 四个层次（全部在本地文件）

```
第 4 层  会话文件（JSONL 树）      ~/.pi/agent/sessions/--<path>--/<ts>_<id>.jsonl   永久
第 3 层  压缩摘要（CompactionEntry） 同一文件内，firstKeptEntryId 之后才进上下文       永久
第 1 层  当前上下文投影              SessionManager.buildSessionProjection()          内存
第 0 层  单次请求的消息数组           convertToLlm() 之后                                内存
```

外加**分支摘要**（`BranchSummaryEntry`）：切分支时把离开的那条分支压成摘要带走。

### 1.2 一次请求的上下文装配（二开前的真实链路）

```
Agent.state.messages
  → agent.transformContext(messages)        ← AgentSession 已链式包裹（agent-session.ts:1721）
  → agent.prepareRequest({context})         ← 装入权威上下文（SessionManager 投影）
  → convertToLlm(messages)                  ← 过滤 UI-only、降级自定义角色
  → normalizeContext({messages})            ← 折成 TranscriptContext
  → streamFn
```

`AgentSession` 对 `transformContext` 的做法值得抄：

```ts
// agent-session.ts:1721
const previousTransformContext = this.agent.transformContext;
this.agent.transformContext = async (messages, signal) => {
  const base = previousTransformContext ? await previousTransformContext(messages, signal) : messages;
  return /* 本层处理 */;
};
```

**这是链式包裹，不是替换**——扩展与产品逻辑可以叠加。记忆注入就应该用同样的方式挂上去。

### 1.3 跨会话检索：今天只有「人工的」

| 能力 | 现状 |
|---|---|
| 继续上次会话 | `/resume`，按 cwd 列文件、选一个（`cli/session-picker.ts`、`findMostRecentSession`） |
| 从某条历史分叉 | `/tree` + `fork`/`clone`（`tree-selector.ts` 1435 行） |
| 跨会话找「上次讨论过什么」 | **没有**。只能人工 grep JSONL |
| 用户偏好/画像 | **没有**。只有 `AGENTS.md`（手写静态上下文）与 settings |
| 语义召回 | **没有** |

**结论：pi 的「记忆」是「结构化 + 可分支 + 可回放」的强项，弱在「跨会话语义检索」与「用户画像」。** 这也是第 2 项唯一真正的价值空间。

### 1.4 已有的两件事会被新系统撞上

| 现有机制 | 触发 | 作用域 |
|---|---|---|
| `transformContext` | 每次请求 | 当前会话内存消息 |
| Compaction | 阈值 / 命令 | 当前会话历史 |
| 分支摘要 | 切分支 | 分支之间 |
| SessionManager 投影 | 每次请求（`prepareRequest`） | 权威上下文 |

**新记忆系统若不明确「和这四者谁先谁后」，一定会打架。** 见第三节。

## 二、差距与设计决策

### 2.1 三个必须先回答的问题

**Q1：既然有会话树和压缩，为什么还要 Redis 短期缓存？**

诚实回答：**当前会话不需要**。pi 的投影已经比「Redis 里存最近 N 条消息」强得多（可分支、可回放、压缩不删原始数据、崩溃可恢复）。

Redis 短期缓存真正有用的场景只有两个：
- **多实例/多端共享**：WebUI + 终端同时看同一会话（此时 `server` 的多附着已经在解决，用不上 Redis）；
- **跨进程快速恢复**：会话文件巨大时，投影计算慢，缓存投影结果。

**建议：把「Redis 滑动窗口」重新定义为「投影缓存（projection cache）」，而不是「会话缓存」。** 键是 `sessionId + leafId`，值是投影结果 + token 估算。这样它才不与会话树冲突，而是加速它。

**Q2：长期记忆到底存什么？**

不要存原始消息（会和会话文件重复、且语义稀释）。存**提炼后的记忆条目**：

```ts
interface MemoryItem {
  id: string;
  kind: "decision" | "preference" | "fact" | "pitfall" | "term";
  text: string;              // 一句话，50–200 字
  embedding: number[];       // 维度随模型
  scope: { project?: string; user?: string; cwd?: string };  // 作用域，必须
  source: { sessionId: string; entryId: string };            // 可溯源，必须
  createdAt: number;
  lastUsedAt: number;
  ttl?: number;
  confidence: number;
}
```

**`source` 是硬要求**：召回的记忆必须能跳回原始会话条目，否则用户无法验证、无法纠正，最终会不信任它。

**Q3：什么时候写入？**

| 时机 | 成本 | 风险 |
|---|---|---|
| 每条消息后 | 极高 | 噪声 |
| 压缩时顺带提炼 | 低（本来就要调模型） | 压缩时机不确定 |
| 会话结束时异步提炼 | 中 | 可能中断（会话没"结束"概念） |
| 显式 `/remember` | 零 | 依赖用户 |

**推荐：压缩时顺带提炼（主）+ 显式 `/remember`（辅）。** 压缩本来就要把一段历史交给模型做摘要，让它在同一调用里多产出一个 `memoryItems[]` 数组，边际成本几乎为零。这是本项最重要的一个洞察。

### 2.2 Redis 与向量库的位置（依赖红线）

`AGENTS.md` + 安装锁生成器把带生命周期脚本的依赖当评审项，允许清单只有 2 条：

```js
["esbuild@0.28.2", ...]
["protobufjs@7.6.6", ...]
```

`faiss-node`、`better-sqlite3` 都带原生编译或安装脚本 → 走白名单评审，且 `.npmrc` 的 `min-release-age=2` 会进一步拖慢。

**两条路线：**

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 外部服务化**（推荐） | Redis/Faiss 跑在 pi 进程之外；pi 只做 HTTP 客户端（用内置 `fetch`） | **零原生依赖**，不触发白名单；可用现成服务 | 需要运维；离线场景不可用 |
| B. 内嵌 | 引 `ioredis` + `faiss-node` | 单机自足 | 触发依赖评审；跨平台预编译麻烦 |

**推荐 A，并且做成可选插件**（第 3 章讲的扩展机制）：不装就完全退化成今天的 pi。

## 三、二开前 vs 二开后的流程对照

### 3.1 请求侧（读记忆）

**二开前**

```
transformContext(messages)            ← 可选裁剪
prepareRequest → SessionManager 投影   ← 权威上下文（含压缩）
convertToLlm → normalizeContext → 模型
```

**二开后**

```
prompt(userText)
  ├─【新】retrieve(query = 最近 N 条用户消息的摘要)
  │      ├─ Redis: 取 projection cache（sessionId+leafId）
  │      ├─ 向量库: top-k 语义召回（按 scope 过滤：project/user/cwd）
  │      └─ 重排 + 去重 + 预算裁剪（硬上限，比如 800 token）
  │
  ├─ transformContext(messages)
  │      └─【新】把召回结果包成一条 system message.sections["memory"]
  │             （用既有分节机制，可被后续补丁替换/删除）
  ├─ prepareRequest → SessionManager 投影（不变）
  ├─ convertToLlm（不变）
  └─ 模型
```

**关键：记忆不走"消息插入"，而走"具名分节"。** 理由：

- 分节可被精确替换（`sections: { memory: null }` 即可清除），不污染转录；
- 每轮刷新召回内容不会让消息数组膨胀（同一分节被覆盖）；
- 压缩时摘要会自然带上它。

### 3.2 写入侧

**二开前**

```
压缩触发（prepareNextTurn）
  → generateSummary() 调 LLM
  → 写 CompactionEntry{summary, firstKeptEntryId}
```

**二开后**

```
压缩触发（prepareNextTurn）
  → generateSummary() 调 LLM
  →【新】同一调用/同一次请求里要求额外输出 memoryItems[]
  → 写 CompactionEntry（不变）
  →【新】异步写记忆：
        ├─ Redis: 更新 projection cache（覆盖式）
        └─ 向量库: upsert（带 source 溯源 + scope + confidence）
```

### 3.3 会话结束/空闲

**二开前**：什么都没有，会话就在文件里躺着。

**二开后**（可选，作为兜底）：
```
agent_end 且 距上次写入 > T
  → 后台任务：对本段新消息做一次轻量提炼（复用压缩提示词）
  → 写入记忆
```

## 四、与既有机制的四条冲突规则（必须写进设计文档）

| 冲突 | 规则 |
|---|---|
| 记忆 vs Compaction | **压缩结果优先**。压缩后的摘要已经包含"该记住的决策"，记忆只补跨会话的部分。若召回条目与当前摘要矛盾，**以当前会话为准**并降低该条目 confidence |
| 记忆 vs 分节补丁 | 记忆只写 `sections.memory` 一个分节，禁用其它分节名 |
| 记忆 vs 用户 `AGENTS.md` | `AGENTS.md` 是**显式指令**，优先级高于任何召回的记忆。冲突时记忆一律丢弃 |
| 记忆 vs 隐私 | 记忆含代码片段/路径，**必须可删除、可导出、可见**。提供 `/memory list`、`/memory forget <id>` |

| P5 | 画像（从记忆条目聚合偏好，注入分节） | 5 |

| **合计** | | **约 25–35** |

### 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 召回噪声污染上下文 | 比不召回更糟 | 严格 top-k（3–5）+ 相似度阈值 + 预算硬上限 |
| 与压缩重复劳动 | 双份 token 成本 | 记忆只在压缩时产出，不额外调用 |
| 隐私/合规 | 记忆跨项目泄漏 | scope 强制 + 默认关闭跨项目 + 显式开关 |
| embedding 服务不可用 | 阻塞请求 | **必须异步 + 失败降级**（召回为空，不影响主流程） |
| 依赖评审 | 卡排期 | 走外部服务化路线 |

### 验收

不要用"连贯性明显提升"这种表述。用三条可判分任务：

1. **跨会话指代**：新会话问"上次我们为什么选了 X 方案"，答案必须包含既有 `MemoryItem` 里的决策点；
2. **术语一致**：同一项目多次会话使用同一自造术语；
3. **干扰测试**：无关项目的历史不得被召回（比召回率更重要）。

## 六、一句话结论

**当前会话不需要 Redis 记忆——会话树 + 投影 + 压缩已经更好。**
第 2 项真正该做的是三件更小的事：**跨会话语义召回（压缩时顺带产出）**、**可溯源的记忆条目**、**用户画像（从记忆聚合，而不是新造一套）**。把范围收窄后，工作量从「一个记忆平台」降到「一个 3000 行的可选插件」。
