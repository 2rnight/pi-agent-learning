# 04 全双工流式交互与状态同步

## 一、二开前：今天的流式其实已经做完了一半

### 1.1 流式的三层来源

```
① 供应商层（pi-ai）
   SSE / WebSocket → AssistantMessageEvent
   { start, text_delta, thinking_delta, toolcall_delta, ..., done | error }

② 运行时层（agent-core）
   AgentEvent
   { agent_start, turn_start, message_start, message_update, message_end,
     tool_execution_start, tool_execution_update, tool_execution_end, turn_end, agent_end }

③ 会话/传输层（coding-agent）
   AgentSessionEvent（在 AgentEvent 之上加了 session/compaction/retry/queue 等）
   → 三种消费者：interactive（TUI）/ print / json+rpc
```

### 1.2 COT（思考过程）今天就已经透传

`AssistantMessageEvent` 里有 `thinking_start / thinking_delta / thinking_end`，`agent-loop.ts` 把它们统一转成 `message_update`：

```ts
case "thinking_start":
case "thinking_delta":
case "thinking_end":
  ...
  await emit({ type: "message_update", assistantMessageEvent: event, message: { ...partialMessage } });
```

再往传输层看，`modes/json-event.ts` 明确做了**瘦身**：

```ts
/**
 * Remove cumulative assistant snapshots from streaming wire events.
 * `message_start` provides the initial message, deltas build it, and
 * `message_end` provides the final authoritative message.
 * Cumulative usage, tool-call ids, and tool names remain available because their size is constant.
 */
```

即：**线上只发 delta，不发累积快照**（省带宽）。`thinking_delta` 是 delta，因此**COT 会外发**。

**结论：需求第 4 项的「COT 与工具状态流式实时透传」，在 RPC/JSON 模式下已经实现。** 需要确认的只是你的客户端是否消费了 `message_update.assistantMessageEvent.type === "thinking_delta"`。

### 1.3 打断（Interrupt）今天已经实现

```
用户 Esc / abort()
  → Agent.abort()  → AbortController.abort()
  → runLoop 中 signal.aborted 检查点：
       ├─ 每个工具执行前
       ├─ 串行执行的每次迭代后（`if (signal?.aborted) break;`）
       └─ 并行执行闭包入口
  → 未执行的工具 → error toolResult "Operation aborted"
  → 当前流 → stopReason: "aborted"
  → 队列里的 steering/follow-up 消息 → 回到编辑器，不丢
```

`agent-loop.ts` 的并行分支里写得很清楚：

```ts
finalizedCalls.push(async () => {
  if (signal?.aborted) {
    const finalized = { toolCall, result: createErrorToolResult("Operation aborted"), isError: true };
    await emitToolExecutionEnd(finalized, emit);
    return finalized;
  }
  ...
});
```

### 1.4 双向通信今天也已经实现两套

| 通道 | 编码 | 特点 | 代码 |
|---|---|---|---|
| **RPC 模式** | stdin/stdout 上的 JSONL | 单客户端、命令/响应 id 关联、事件流、扩展 UI 转发 | `modes/rpc/` |
| **protocol/client/server** | 4 字节长度 + CBOR | 任意有序字节传输、多客户端、多展示附着、带外状态 | `protocol`/`client`/`server` |

`protocol` 的设计已经考虑了「多端同时看同一个 Session」：

```
Session target = { serverId, sessionId, attachmentId }
```

`server/README.md` 明确："A Session may have multiple presentation attachments."

### 1.5 那到底缺什么？

真实缺口只有四个，而且都很具体：

| 缺口 | 说明 |
|---|---|
| **没有现成的 WebSocket 传输** | `protocol` 只定义 `ByteTransportFactory`，仓库里 `WebSocket` 只出现在 SDK/settings/radius-relay，**没有一个 WS 传输实现**（`grep -rn WebSocket packages/protocol/src` 为空） |
| **RPC 是单客户端、无重连** | stdin/stdout 管道，断即死；不能多端接入同一会话 |
| **无「状态恢复」语义** | 重连后要什么？重放事件？还是拉快照？**没有定义** |
| **无打断的确认/回滚协议** | `abort` 是单向信号，客户端不知道"到哪一步停下、哪些工具已提交" |

## 二、二开思路：不要新建协议，只补传输与恢复

### 2.1 为什么不要自己设计一套 WS 消息格式

`protocol` 已经解决了：版本握手、路由围栏、请求/响应关联、取消、订阅更新、带外附着、严格 JSON 校验、16MiB/64 层限制。

自己再设计一套会丢掉这些，并产生两套不兼容的远程协议。**正确做法是实现一个 `ByteTransportFactory`：**

```ts
// packages/client/src/websocket.ts（新增）
import type { ByteTransportFactory } from "@earendil-works/pi-client";

// 真实契约（packages/client/src/transport.ts）：
//   ByteTransport { send(chunk: Uint8Array): Promise<void>; close(): void }
//   ByteTransportHandlers { onData(chunk: Uint8Array): void; onClose(): void; onError(error: Error): void }
//   ByteTransportFactory = (handlers) => ByteTransport | Promise<ByteTransport>
//   注释要求：send 必须按调用顺序投递；close 重复调用必须无害；工厂返回已连接且已认证的传输。

export function webSocketTransport(url: string): ByteTransportFactory {
  return async (handlers) => {
    const socket = new WebSocket(url);
    socket.binaryType = "arraybuffer";
    const opened = new Promise<void>((resolve, reject) => {
      socket.addEventListener("open", () => resolve(), { once: true });
      socket.addEventListener("error", () => reject(new Error("websocket open failed")), { once: true });
    });
    socket.addEventListener("message", (e) => handlers.onData(new Uint8Array(e.data as ArrayBuffer)));
    socket.addEventListener("close", () => handlers.onClose(), { once: true });
    socket.addEventListener("error", () => handlers.onError(new Error("websocket error")));
    await opened;                                  // 工厂返回时必须是"已连接"

    return {
      async send(chunk) {
        socket.send(chunk);                        // WS 保证有序
      },
      close() {
        socket.close();                            // 重复调用无害
      },
    };
  };
}
```

一个文件 + 一层适配，就接上了既有的 CBOR 协议。**这是本项工作量最被低估的地方：它本来就快要做好了。**

### 2.2 状态恢复：必须定义三件事

重连后客户端要能"接上"，需要三个明确规则：

**① 快照 + 增量（推荐）**

```
客户端重连（带 lastSeq）
  → 服务端：
     ├─ 若 lastSeq 在保留窗口内 → 重发缺失事件（增量）
     └─ 否则 → 发一个 snapshot（当前消息数组 + 进行中的工具状态）+ 后续增量
```

**② 事件序号（seq）**
`protocol` 的订阅更新目前是"不透明更新"，**需要在应用层加单调递增 seq**（协议层不拦，因为它不解析 payload）。

**③ 「进行中」的显式状态**
pi 有 `AgentState.streamingMessage` 与 `pendingToolCalls`，正好可以作为快照里"进行中"的部分：

```ts
interface SessionSnapshot {
  seq: number;
  messages: AgentMessage[];             // 已完成的历史
  streaming?: AgentMessage;             // 正在生成的 assistant 消息（partial）
  pendingTools: Array<{ toolCallId, toolName, startedAt }>;
  isStreaming: boolean;
  model: string;
  thinkingLevel: string;
}
```

**注意**：`streamingMessage` 是"部分消息"，重连后可以直接渲染成"正在输出"，而不必重放几百个 delta。这正是它存在的原因。

### 2.3 打断的增强：从「单向信号」到「可控停止」

**今天**：`abort()` 立即中断，工具结果被标记 aborted，队列消息回到编辑器。客户端只能看到 `stopReason: "aborted"`。

**建议增强**（这才是需求里"打断与状态恢复"的实质）：

| 能力 | 实现 |
|---|---|
| 分阶段打断 | `abort({ phase: "after-current-tool" })`，避免半途杀掉正在写文件的操作 |
| 打断原因透传 | 事件的 `abortReason: "user" \| "timeout" \| "budget"` |
| 已提交副作用清单 | `agent_end` 时带 `committedTools: [{toolCallId, sideEffect: true}]`，客户端可提示"已修改 3 个文件" |
| 打断后可继续 | 已有：队列消息 + `continue()`（`Agent.continue()` 支持从非 assistant 尾部继续） |

**分阶段打断的价值**：`edit` 工具写到一半被 SIGKILL 会留下半写文件。虽然 `withFileMutationQueue` 是串行的，但它不保证原子性。所以"在当前工具结束后停"应该成为默认，而不是"立即停"。

### 2.4 二开前 vs 二开后的完整流程

**二开前（RPC，单客户端）**

```
客户端进程 A ──spawn──► pi --mode rpc
   ├─ stdin:  {"id":"1","type":"prompt",...}
   ├─ stdout: {"id":"1","type":"response",...}
   ├─ stdout: 事件 JSONL（message_start / message_update{deltas} / tool_execution_* / ...）
   └─ 断开 → pi 进程收到 EOF → 结束（无法重连、无法第二端接入）
```

**二开后（WebSocket + 多端）**

```
浏览器/IDE/终端 各一个客户端
   │  WebSocket（有序字节）
   ▼
网关（Node，30 行）
   └─ webSocketTransport → Client.connect({ serverId, transportFactory })
        │  CBOR 帧（既有 protocol）
        ▼
pi-server（既有，不透明路由）
   │  附着管理：attach → attachmentId（带外下发）
   ▼
Session worker（既有的 durable / AgentSession 宿主）
   │
   ├─ 事件 → protocol 订阅更新（应用层加 seq）
   └─ 命令 → Client.request({ serviceId, member, args })

重连：
   客户端带 lastSeq 重连
     → 在窗口内：补发缺失增量
     → 不在窗口内：拉 SessionSnapshot（含 streamingMessage + pendingTools）后再增量

打断：
   客户端发 abort（可带 phase）
     → Session worker 在检查点停下
     → 下发 agent_end { abortReason, committedTools }
     → 队列消息保留，客户端可再发 continue

多端：
   终端与浏览器同时 attach 同一 sessionId
     → 各自 attachmentId，各自 seq
     → 一端 prompt，两端都收到事件（广播由 server 的附着管理负责）
```

### 2.5 一个必须提前决定的取舍：谁来承载「网关」

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| **A. 薄网关**（推荐） | Node WebSocket server，仅做 transport 适配，转发给既有 `pi-server` | 协议单一、逻辑不重复 | 多一跳 |
| B. server 内建 WS | 直接在 `pi-server` 加 WS 监听 | 少一跳 | server 目前"不透明路由"，加 WS 会引入传输耦合 |
| C. 浏览器直连 | 让 `client` 在浏览器里跑 | 最少代码 | Node 的 `net`/`Buffer` 依赖需处理；`protocol` 的 CBOR 在浏览器可用，但 `client/unix` 不可用 |

**推荐 A**，因为 `server/README.md` 的设计意图就是"服务器只是管道，不理解业务"，B 会破坏这一点。

## 三、工作量、风险、验收

| 项 | 人日 |
|---|---|
| WS 传输实现 + 网关 | 2 |
| 事件 seq + 增量重放 | 2 |
| SessionSnapshot（含 streaming/pendingTools） | 2 |
| 分阶段打断 + abortReason + committedTools | 2 |
| 多端附着联调（复用 server 的 attach） | 1 |
| 测试（断线重连、多端、打断） | 1 |
| **合计** | **6–10** |

### 风险

| 风险 | 缓解 |
|---|---|
| 事件重放导致 UI 重复渲染 | 客户端按 seq 幂等；`message_start` 的 id 去重 |
| 增量缓冲区占内存 | 保留窗口（如最近 500 条 / 5 分钟），超窗走快照 |
| 快照与增量之间的竞态 | 快照必须带 `seq`，且服务端在发送快照期间缓冲增量 |
| 多端同时 prompt | `ConversationBusy` 语义（durable 已有）；或按 attachment 做写锁 |
| WS 心跳与代理超时 | 应用层 ping/pong（`pi-protocol` 本身没有 ping 帧；`pi-env` 的帧协议 type 6 才是 ping，可借鉴其设计） |

### 验收

1. **断线 30 秒后重连**：界面从"正在输出"正确恢复，不重复、不丢失。
2. **双端同时观察**：一端 prompt，两端事件顺序一致（按各自 seq 断言）。
3. **打断粒度**：`after-current-tool` 模式下，正在执行的 `edit` 必须完成，后续工具不执行。
4. **COT 可见性**：客户端能收到并渲染 `thinking_delta`（这条今天就该通过，用它做回归基线）。

## 四、本章最重要的一句话

**第 4 项需求的 70% 已经存在于仓库里**：COT 流式、工具状态流式、打断、双向协议、多端附着。"WebSocket 全双工"缺的只是一个传输实现和一套恢复语义。

所以这一项应该被重新定义为：**「给既有 CBOR 协议补一个 WS 传输 + 定义快照/增量恢复 + 把 abort 从信号升级为协议」**，而不是"从零做全双工通信"。前者 6–10 人日，后者会被估成 30 人日并做出一套重复的协议。
